# 03 · 阵营与模式现状

> 这份文档回答两件事：**现在有哪些阵营、它们怎么被用**；**现在有哪些模式、它们缺什么**。
> 结论先行：阵营框架是齐的，模式这层是空的。

---

## 一、两层结构

```
gteams（团队）           ← 谁来计分、谁和谁敌对、显示什么颜色
   │  25 个，注册在 sh_gteams.lua
   │  玩家侧：ply:GTeam() / ply:SetGTeam()
   ▼
BREACH_ROLES（角色表）    ← 一个阵营下有哪些具体兵种，每个兵种的属性
   │  静态 17 块 + 动态 3 块
   │  生效入口：ply:ApplyRoleStats(role)
   ▼
具体玩家
```

两层是**松耦合**的：角色定义里带 `team = TEAM_XXX` 字段，`ApplyRoleStats` 时才会写进 `gteams`。
所以改了 `BREACH_ROLES` 里的 `team` 字段，玩家的团队归属才会跟着变。

## 三、`BREACH_ROLES` 角色表

### 结构

```lua
BREACH_ROLES.<阵营大写> = {
    <阵营小写> = {
        name  = "显示名",
        color = Color(...),
        roles = {
            { name = role.常量, team = TEAM_XXX, weapons = {...}, level = 0, max = 6, ... },
            ...
        }
    }
}
```

### ⚠️ 命名约定（硬性，写错就崩）

支援阵营系统用这一行取表（`sv_module.lua:3288`）：

```lua
return BREACH_ROLES[string.upper(supname)][string.lower(supname)].roles
```

即 **外层 key 必须等于内层 key 的大写**。`BREACH_ROLES.NTF.ntf.roles` ✅，`BREACH_ROLES.NTF.NTF` ❌。

硬编码特例：
- `"FBI"` / `"FBIAgents"` → `BREACH_ROLES.FBI_AGENTS.fbi_agents.roles`
- `"FBI_SHTURM"` → `BREACH_ROLES.FBI.fbi.roles`

### 阵营块清单

**静态定义（`sh_roles_scp.lua`，17 块）**

| 块 | 内层 key | 主模式是否使用 |
|---|---|---|
| `MTF` | `mtf` | ✅ `SetupPlayers` tab[2] |
| `SCI` | `sci` | ✅ tab[3] |
| `SPECIAL` | `special` | ✅ tab[6] |
| `SECURITY` | `security` | ⚠️ tab[4]，16 槽下恒为 0 |
| `CLASSD` | `classd` | ✅ tab[5]，兜底 `OTHER.other.roles[1]` |
| `SCP` | `scp` | ❌ 主模式走 `RegisterSCP()`，不走这张表 |
| `NTF` `CHAOS` `GRU` `GOC` `DZ` `COTSK` | 同名小写 | ✅ 支援阵营 |
| `FBI_AGENTS` | `fbi_agents` | ✅ 支援阵营（`FBI`） |
| `FBI` | `fbi` | ✅ 支援阵营（`FBI_SHTURM`） |
| `OBR` | — | ❌ 未接入 |
| `OTHER` | `other` | ✅ 仅作 Class-D 兜底 |
| `MINIGAMES` | `minigame` | ⚠️ 彩蛋模式用，**只有 roles[1..3]** |
| ~~`OSN`~~ | — | ❌ 显式置 `nil` |

**动态注册（在 `sh_roles_scp.lua` 文件末尾挂钩）**

| 模块 | 注册的块 | 说明 |
|---|---|---|
| `sh_nu7.lua` | `BREACH_ROLES.NU7 = {nu7 = ...}` | 8 个兵种，模板继承自 `NTF.ntf.roles` |
| `sh_alpha9.lua` | `BREACH_ROLES.ALPHA9 = {alpha9 = ...}` | MTF-Alpha9 |
| `sh_theory_erasure_goc.lua` | `BREACH_ROLES['GOC"理论抹除"小组'] = {theory = ...}` | ⚠️ 外层 key 是中文，**不符合大写约定，支援系统取不到** |

这解释了"源码里数到 96 个 `role.*` 常量，验收报告写 132 个角色"的差异——动态模块补了剩下的。

## 四、主回合的人数分配

### 调用链

```
RoundTypeUpdate()           -- sv_round.lua
  └─ activeRound = ROUNDS.normal
       └─ .setup()  → SetupPlayers( GetRoleTable( #GetActivePlayers() ) )
```

### `GetRoleTable(all)` 返回 6 个数字

| 索引 | 含义 | 对应阵营块 |
|---:|---|---|
| 1 | SCP 数量 | `RegisterSCP` 注册的 `SCPS` 列表 |
| 2 | MTF 数量 | `BREACH_ROLES.MTF.mtf.roles` |
| 3 | 研究员数量 | `BREACH_ROLES.SCI.sci.roles` |
| 4 | 安保数量 | `BREACH_ROLES.SECURITY.security.roles` |
| 5 | Class-D 数量（剩余） | `BREACH_ROLES.CLASSD.classd.roles` |
| 6 | 特殊角色数量 | `BREACH_ROLES.SPECIAL.special.roles` |

### 公式

```lua
scp = all < 25 ? 1 : all < 35 ? 2 : 3

if #player.GetAll() <= 14 then
    mtf = floor(all * 0.30);  res = floor(all * 0.30);  specialres = 0
else
    res = floor(all * 0.25);  mtf = floor(all * 0.14);  sec = floor(all * 0.24)
    if #player.GetAll() <= 18 then mtf = mtf + sec; sec = 0 end   -- ← 关键
end

classd = all - res - mtf - sec
```

### ⚠️ 16 槽的实际结果

服务器 `+maxplayers 16`，于是 `mtf + sec` 合并那一行**必然触发**：

| 人数 | SCP | MTF | 研究员 | 安保 | Class-D | 特殊 |
|---:|---:|---:|---:|---:|---:|---:|
| 2 | 1 | 0 | 0 | 0 | 1 | 0 |
| 6 | 1 | 1 | 1 | 0 | 3 | 0 |
| 10 | 1 | 2 | 2 | 0 | 5 | 0 |
| 14 | 1 | 3 | 3 | 0 | 7 | 0 |
| 16 | 1 | 5 | 3 | **0** | 7 | 0（50% 概率 1） |

> **结论：`SECURITY` 阵营在 16 槽配置下永远分配不到玩家**，它的角色表是死代码。
> 若要启用安保阵营，要么扩槽到 19+，要么改 `GetRoleTable` 的合并条件。

### `SetupPlayers` 的执行顺序

```
1. 剔除有 SCP 惩罚的玩家（GetPenaltyAmount > 0）
2. SCP        : 从 SCPS 池随机，scp:SetupPlayer(ply)
3. MTF        : 按玩家等级从高到低，按 importancelevel / max / customcheck 挑兵种
4. 研究员     : BREACH_ROLES.SCI.sci.roles
5. 特殊角色   : BREACH_ROLES.SPECIAL.special.roles（tab[6] > 0 时）
6. 安保       : BREACH_ROLES.SECURITY.security.roles（16 槽下不执行）
7. Class-D    : BREACH_ROLES.CLASSD.classd.roles，兜底 OTHER.other.roles[1]
8. 剩余玩家   : SetupNormal() + SetSpectator()
9. net.Start("RolesSelected") 广播
```

## 五、支援阵营（Support）系统

主回合进行到中途，玩家可以**选择加入某个支援阵营**，这是 SCP:SL 的经典设计。

| 环节 | 位置 |
|---|---|
| 名单初始化 | `sv_rounds.lua` 的 `SUPPORTTABLE`：`GOC / FBI / CHAOS / NTF / DZ / COTSK / GRU` |
| 取角色表 | `sv_module.lua:3288` `GetSupportRoleTable(supname)` |
| 可选列表 | `GetAvailableSupports()` 过滤掉本轮已用过的 |
| 客户端界面 | `cl_support_selection.lua`（12 KB） |
| 稀有度池 | `BigRoundOnlySupports` / `FirstRoundOnlySupports` / `SecondRoundOnlySupports` / `RareSupports` / `NotRareSupports` |

`SUPPORTTABLE[sup] = true` 表示本轮该支援已入场，不可重复。
`SPAWNEDPLAYERSASSUPPORT` 记录已作为支援出场的玩家，防止刷。

## 六、模式（`ROUNDS`）现状

### 表结构

`sv_rounds.lua` 里 `ROUNDS = { <key> = { name, setup, init, roundstart, postround, endcheck } }`

| 回调 | 时机 |
|---|---|
| `setup` | 回合开始前，分配玩家、重置全局状态 |
| `init` | 初始化模式常量（超时、可否逃跑、掉落武器等） |
| `roundstart` | 正式开局，开门、启动定时器、放音乐 |
| `postround` | 结算（MVP 统计等） |
| `endcheck` | 每 tick 检查胜负条件，调 `Breach_EndRound(reason)` |

### 现有条目：只有 2 条

| key | name | 状态 |
|---|---|---|
| `normal` | Containment Breach | 🟡 能跑，但 `endcheck` 整段被注释 |
| `ww2tdm` | WW2TDM | 🔴 本图必崩 |

### `ulx forceround` 承诺的 8 个名字

`sh_ulx.lua:829` 的补全列表：
```
normal, normalevent, ww2tdm, hl2tdm, uiugoc, event, ny_event, furry_event
```

实际 `ROUNDS` 里只有 `normal` 和 `ww2tdm`，**其余 6 个不存在**。
`RoundTypeUpdate()` 有兜底（`if !activeRound then activeRound = ROUNDS.normal end`），
所以不会崩，只会静默退化成普通回合。

### 模式选择逻辑

```lua
RoundTypeUpdate()
    chance = random(0, 100)
    if chance > 10 then  activeRound = ROUNDS.normal       -- 90%
    else
        if random(0,2) == 0 and SPAWN_NAZI_1 and SPAWN_USA_1 and MINIEVENTPROP then
            activeRound = ROUNDS.ww2tdm                     -- 仅当地图有点位
        else activeRound = ROUNDS.normal end
    end
    if forceround then activeRound = ROUNDS[forceround] end -- 管理员强制
```

本图（`rxsend_site19-1`）缺 `SPAWN_NAZI_1` / `SPAWN_USA_1` / `MINIEVENTPROP`，
所以**永远走 `normal`**。

## 七、缺口汇总（按优先级）

### P0 · 阻塞上线
1. **玩家进不来** —— 至今 0 次成功连接，UDP 30679 映射未验证。
2. **误触发即崩** —— `ww2tdm` 及其他未完成模式应在上线前从入口移除，或补全角色表。

### P1 · 主模式不完整
3. `normal.endcheck` 没有胜负判定 —— 目前只能靠通用 `WinCheck()`，没有阵营专属条件（比如"SCP 全灭 / MTF 全灭 / Class-D 逃生成功"）。
4. 18 个 SCP 缺出生点，全部回落到 `SPAWN_SCP_RANDOM` 默认表 —— 意味着 SCP-173/106/939 等可能生成在奇怪位置。

### P2 · 阵营层
5. `SECURITY` 在 16 槽下不可达（改公式或扩槽）。
6. `OSN` 团队存在、角色表被 `nil` 掉。
7. `AR` / `CBG` / `COMBINE` / `RESISTANCE` 只有团队没有角色，也没有分配逻辑。
8. `BREACH_ROLES['GOC"理论抹除"小组']` 的 key 不符合约定，支援系统取不到。

### P3 · 模式层
9. 6 个模式名（`normalevent` / `hl2tdm` / `uiugoc` / `event` / `ny_event` / `furry_event`）没有实现。
10. 每个新模式还缺地图点位数据（不能靠抄别的地图）。
